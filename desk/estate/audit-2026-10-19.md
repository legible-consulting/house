## 2. Architecture

Ranked by what it costs if left.

1. **The core is the critical path.** Seven contracts (S1, S3, S4, S5, D3, O1, O3) name
   `core/services.md`, `core/voice.md`, `core/identity.md` or `core/terms.md` as an Input;
   none exists. Nothing in sell can produce until C1 does. The four files are short; one
   session with Jamie's answers writes them.
2. **D2 is one tier wide.** The blueprint renders `site` fully; `app` and `platform` render
   a README and the answers file. Four of the five live repos are `app` or `platform`.
   Adopting them (D4's next step) pins them to a tier with no content, and a later
   `copier update` would merge a template README over each client's own README unless
   `copier.yml` sets `_skip_if_exists: [README.md]`.
3. **The blueprint tag trails `main`.** `v0.1.0` predates the guards; a site rendered today
   gets no `.claude/` (`site-proof` is in that state). Tag `v0.2.0`.
4. **Second homes without a check.** Each guard exists three times (global, house, blueprint
   `site`), kept identical by hand; `desk/mani.yaml` is hand-written; `cloud.sh` is pasted;
   the blueprint and `.github` checkouts sit on merged branches and `library` is dirty. Each
   has a why; none has a check. One `check.yml` job that fetches blueprint's site-tier hooks
   and diffs them against `.claude/hooks/` closes the one that bites first.
5. **The manifest is incomplete.** `courseday`, `firedough` and `site-proof` are in the org
   and not in `mani.yaml`; design §3 says a repo not in the manifest does not exist.
   `drift.sh` reads only `live`, so D4's "every dormant repo archived, secret-free and named"
   is never checked. 22 repos remain on `k0d0minio` (design said 9), `icm-board` among them;
   it retires only once one real deal has walked the new folders.
6. **The dashboard is not yet a desk.** One table, a new preview URL every six hours behind
   Vercel Authentication, no stable address, no glance, no alert path. `vercel alias` to one
   fixed URL in `dashboard.yml` is the first step; `sweep-deadlines.yml` the second.
7. **Chain break.** `clients/<slug>/tickets.md` is D1's Input and C2 names it; no module's
   Outputs produce it. It belongs to S3 (scope → tickets) or S4.
8. **Stale open items.** 2FA is required on the org and `GPardas` is not a member; the
   `remi21` Vercel team is visible from this login. Two of five items are decided.

## 3. Security

1. **Six client repos are public:** berceo, agorasim, vinecliff-vineyard, remi-ai, courseday,
   firedough. Design §4 sets "sites public, apps and platforms private"; all six are `app`
   or `platform` (remi-ai is a company's product; berceo takes payments). The trade was
   free rulesets and free secret scanning, and secret scanning and push protection are
   **disabled** on all eight public repos (API, today). The estate pays the exposure and
   does not collect the benefit. Per repo, Jamie decides: private (rulesets lost on Free;
   `guard-main.yml` becomes the gate and is not yet written) or public with scanning and push
   protection switched on (free, one API call each).
2. **The secrets guard has a hole in the mode this machine runs in.**
   `guard-plaintext-secrets.sh` is registered on Write, Edit and MultiEdit. A Bash heredoc
   (`cat > file <<EOF`) writes a file and is never scanned, and auto mode tells the agent to
   prefer Bash for edits. Register the same guard on Bash and scan `tool_input.command`,
   heredoc body included, in all three copies.
3. **The session token is an org owner.** The local `gh` token carries `admin:org`,
   `delete_repo`, `repo`, `workflow`, and every auto-mode session runs under it.
   `confirm-git-writes.sh` asks before merges, releases and deletes, not before
   `gh repo edit --visibility`, `gh api -X PATCH orgs/…` or `gh secret set`. A
   prompt-injected page in an O1 session could flip a repo public. The org move is done:
   re-login with `repo, workflow` for sessions and keep an admin login for runbook steps;
   or add those verbs to the confirm hook.
4. **The house's `main` has no protection** (private, Free), and the house's
   `.claude/settings.json` carries no `confirm-git-writes`, so a cloud session can push or
   force-push `main` with no prompt. The boundary allows committing words to `main`; it does
   not allow rewriting it. Ship the confirm hook in the house; write `guard-main.yml`.
5. **`k0d0minio/garmani` tracks `.env` in a public repo.** Today it holds one public URL.
   Untrack it before the next value is a secret.
6. **Public repos with no CI of their own.** `blueprint` has no workflow; `.github`'s only
   workflow is `workflow_call`. GitHub's own scanning (item 1) covers secrets. A `render.yml`
   on blueprint that renders each tier into a scratch dir and runs actionlint on the result
   is the walk test the template lacks.
7. **Holding, for the record:** Actions pinned to SHAs with `contents: read` and
   `persist-credentials: false`; the cloud environment holds no secrets; `.env*` denied to
   Read; every live clone ignores `.env.local`; 2FA required; repo creation owners only;
   PAT policy fine-grained only; `library` and `house` private.

## 4. ICM

1. **18 of 19 contracts say "Process: defined when the module is built."** The CI contract
   check passes on headings, so the house reads as complete and is not. The goals file's own
   failure test, "a folder is not enough to start a module cold", is true today for 14
   modules. The fix is not 18 processes written up front. Mark each contract
   `status: stub | built` in frontmatter (the desk then shows the count, and the frontmatter
   job starts checking contracts too), and write a process only from a real walk: motoark for
   S2 → S5, vinecliff for D1.
2. **What holds:** the lexicon; boundaries and rules with their whys and dates; the routing
   table; human gates; no orchestrator; `library` read-only; path-scoped rules; every
   Output declared. A cold agent orients in one read.
3. **Inputs that name nothing.** The contract's promise is that Inputs are enough; today most
   Inputs are files that do not exist (§1). The honest contract names what exists and what
   the stage must produce first.
4. **One home per fact is kept for rules and broken for state** (architecture 4). The rule is
   right; the check is missing.
5. **Unattended writes to `library` are ungated** (two-repo sessions load no hooks, and the
   repo is read-only by rule). Raw captures and verdicts belong in the house. Bears on idea 1.

## 5. The three new ideas, placed

**Idea 1 · Links from the phone, analysed and stored.** This is O1's intake, and O1 is a
stub, so this is the reason to build it. Shape: the phone shares a link to one place the
stack already reaches (a Gmail label, or one Google Sheet named `research-inbox`); a
scheduled cloud routine in `legible` with the house attached reads it, fetches the page as
text, writes `operator/research/inbox/<date>-<slug>.md` with a draft verdict
(adopt · watch · decline, `recheck` date, source path) and opens one PR; Jamie's merge is the
gate, and the merged file moves to `verdicts/` or `concepts/`. The home is the house, not
`library` (ICM 5). The boundary gains a fourth unattended run, "the research intake, which
only opens a PR", with its why. Needs a fetch-to-text tool in `cloud.sh`. Half a day once
C1 exists; the verdict template needs `core/services.md` to say "could build for a client".

**Idea 2 · Gates not at the bottom, and bigger.** Read as the Claude desktop app's
confirmation prompts and end-of-turn buttons (the merge and PR gates), which sit at the foot
of a long transcript. The repo cannot move the app's own UI; a mod can: a band above the
prompt listing the session's pending gates (asks, open PRs awaiting a merge), larger than
the inline prompt. The `plugin-authoring` skill builds exactly that, in its own session,
outside the house. If the reading is wrong and this is about the dashboard's gates, it folds
into idea 3 as a "Gates" panel at the top of Jamie's view.

**Idea 3 · The dashboard as the salesmen's sales floor.** This is S1 plus C3's roles and the
goals' tension 2 (who commits on a salesman's behalf). Three things before code:

- a. **S1's model.** The prospect fields, the statuses a salesman moves through, "ready for
  Jamie", who sourced it, commission owed. That is `target-profile.md`, `cadence.md` and a
  `prospect` schema. One session with Jamie's answers; the pitch salesmen see needs
  `core/services.md` and `core/voice.md`.
- b. **One home per fact, resolved by stage.** Before handoff the prospect pool lives in a
  database the dashboard owns. At "ready for Jamie" the dashboard opens one PR that creates
  `clients/<slug>/record.md` at `stage: prospect` under a bot identity (fine-grained PAT or
  a GitHub App), and Jamie's merge is the handoff. The folder is the record from that moment;
  the database is the record before it. No commit per status change; the identity question
  closes.
- c. **Auth and exposure.** A salesman is not a Vercel team member, so Vercel Authentication
  on a preview cannot be the door. The dashboard needs its own sign-in (Neon Auth or
  Supabase Auth, both in the stack) and a production domain; the page names clients, so role
  scoping is the security work, not the UI. Astro stays and gains a server part on Vercel.

Order: a, then C1's services and voice, then b and c. Three to four weeks to a first
salesman working the pool; that is the 90-day signal with the longest lead, so it starts
right after the core.
