# 1.1 Starting the Build Process

*Building Your Stack › Module 1: Custom Interfaces · Author: Jake Van Clief · Source: text lesson*

## Summary

A fork lesson. Start from one recurring pain (finding a file, seeing its status, returning to work from another device) and choose either a custom interface or remote access. For the interface route the learner drafts a small product requirements document, planning only, using a three-file fictional script pipeline with statuses draft, needs review and ready. The lesson's own animation workspace is cited as the interface example, where scripts flow through specs, builds and renders.

## Core concepts

- **Pain first:** pick the control that removes a repeated problem, not a tool.
- **Planning only:** the first run marks unknowns and proposes one acceptance check, and does not build; repository choices wait for lesson 1.2.
- **A PRD template exists:** the lesson supplies a prompt that asks for what and why, target user, existing repos to borrow from, stack suggestions, features to cut, and phases from a minimal first version to polish. I am describing, not reproducing, it.
- **Expected output:** a short requirements file naming inputs, the smallest useful view, exclusions and a test that each listed item opens the right file with its recorded status.
- **Review step:** strip invented requirements and check whether a folder or spreadsheet already solves the pain.

## Frameworks and methods

Choose path, scope one view, draft the PRD, review and cut, then research in 1.2.

## Tools, settings and resources

- **Product requirements document prompt** — the lesson's starting prompt for Claude Code or another assistant.
- **Premium Vault, Foundation and history lessons** — linked context.

## Apply to icm-workshop

- **C3 desk:** the "list status and open the matching file" view is a miniature of the desk's Friday review and dashboard; adopt the smallest-view-first scoping for C3 rather than a large dashboard build.
- **Boundary — never build an orchestrator:** the check "does a folder or spreadsheet already solve it?" is a useful guard to keep before any dashboard code is written.
- **Boundary — runs from anywhere:** the fork to remote access is directly relevant; see Module 2.
