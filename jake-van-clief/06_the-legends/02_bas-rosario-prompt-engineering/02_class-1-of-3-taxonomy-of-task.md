# Class 1 of 3: Taxonomy of task types

*THE LEGENDS › 2. Bas Rosario – Prompt Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

Bas argues that a prompt's shape is just the list of things the model needs from you to hit a particular definition of "good", and that definition changes with the kind of task. He sorts everyday asks into eight kinds, adds modality (text, image, audio and so on) as a cross-cutting axis, and demonstrates with one pile of customer feedback rewritten five ways. The learner leaves able to label any ask with a type and say what its prompt must carry.

## Core concepts

- **Eight task kinds:** problem-solving, math, research, writing, creative, coding, structured output and planning. Each is distinguished by a giveaway question about what the output is for (a checkable answer, a calculation, a survey of sources, polished words, surprise, running code, machine-readable data, a sequence of decisions).
- **Shape equals requirements:** the "one thing" a prompt must carry differs by type, for instance an audience and voice for writing, a language and a pass condition for coding, exact fields for structured output, a goal, horizon and success measure for planning.
- **Modality is an extra layer:** a non-text task keeps its type and gains the rules of its medium.
- **Same input, five definitions of good:** the demonstration uses forty feedback items to show hypotheses with evidence, a customer update in a set register, a fixed-column table, a sourced literature check, and a dated plan with measures.
- **People live in two or three types:** Bas predicts most learners use a couple of kinds heavily and ask for the rest in the wrong shape.
- **Verify, don't just ask:** answers for calculation and research should be checked against a calculator, tested code or the cited sources. The lesson notes that some reasoning models do not need "think step by step" style nudges; what matters is an inspectable answer with evidence.

## Frameworks and methods

1. Take a real ask and name its type by asking what the output is for.
2. Note the modality if it is not text.
3. Check that the prompt carries the one requirement that type needs.
4. Use the Praxis technique index, finder and patterns pages to pick a named technique; the lesson pairs techniques with types but treats them as options, not rules.
