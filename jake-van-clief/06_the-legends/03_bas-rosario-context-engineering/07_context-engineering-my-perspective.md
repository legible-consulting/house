# CONTEXT ENGINEERING: My perspective

*THE LEGENDS › 3. Bas Rosario – Context Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

Bas describes how he uses rung two daily: every piece of model work begins with a room written down before the work starts, and in ICM terms that room is a CONTEXT.md plus a stage contract. He names the line he writes first (the exclusion of the model's own memory), what he thinks is overrated (a bigger window) and underrated (writing down what bad looks like). He ends with the limit that a saved room is a static file, setting up the memory series.

## Core concepts

- **Write the room before the work:** what a step reads, does, hands on and must not touch is recorded in a file so it opens the same tomorrow, for a teammate, and on a bad model day. The examples sit in their own file so they travel between projects.
- **First fence is memory:** a model allowed to recall from training fills gaps with confident, undated claims, so his rooms begin with a rule to use named sources and say so when something is missing.
- **Overrated: the bigger window.** Pasting a whole folder costs on every turn and thins attention on the rest; the best edit is often a cut. The application note warns that costs and loading behaviour depend on the product.
- **Underrated: line seven.** Keeping rejected drafts under a labelled "bad" line gives the edge of the target; he also attaches the failure that caused each rule to the rule itself.
- **Monday plan:** write the seven lines for your most-used prompt into a file, run only the file for a week, and paste every rejected draft under line seven with one reason.
- **The edge:** the file does not learn; nothing here decides what persists between windows, which is the topic of series three.

## Claims and evidence

- Verified beats confident, so exclude the model's memory — author's working practice — the application note says saved rooms do not guarantee source-only behaviour.
- A week of pasted rejects gives a better room than a fresh prompt — author's projection — unverified.

## Apply to icm-workshop

- **Adopt** the rule-with-its-failure habit; it matches the goals file's requirement that a rule carries its own why and date. Each house rule in C1 should name the failure that created it.
- **Adopt** the "use only these sources, otherwise say so" first fence in module contracts that produce client-facing artefacts (S2, S3, S4), where invented facts would be costly.
- **Adopt** the rejected-drafts habit for client artefacts: keep rejected proposal drafts in a reference file, not in git history alone.
- The point that the room is a static file frames the memory work for C2; see the memory series notes.
