# CONTEXT ENGINEERING: Where this fits in ICM

*THE LEGENDS › 3. Bas Rosario – Context Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

Bas maps context engineering onto ICM's Inputs table, using the problem of a 150-line voice guide of which a step needs only about 60. In the ICM conventions, each stage lists the file to read, which section to load, and why, so the unneeded remainder is simply never loaded. He shows that these three labels line up with his seven-line room (tools to use, smallest useful form, does this output need it). He is careful about what the table does not hold: good and bad examples live in separate reference files, and a person still decides what earns a place.

## Core concepts

- **Selection on the contract's door:** an Inputs entry names a file, the section to load, and the reason, making what a stage reads explicit, editable and auditable.
- **Prevention rather than compression:** the method avoids loading irrelevant material in the first place instead of summarising it afterward. The stated rule is that an agent loads only the context needed for the current stage.
- **Instruction, not enforcement:** the list states intended behaviour; verify actual reading through the tool's visible actions or source references.
- **Three labels versus seven lines:** the table covers sources, but not the good or bad example lines, which belong in a reference file the table points to.
- **Working inputs versus references:** inputs hold material for this task; references hold reusable guidance. Marking that difference up front gives later work a place for each.
- **Human still decides:** the Why column accepts any sentence, so the three admission questions remain a person's job.

## Frameworks and methods

1. For each stage, write File / Section to Load / Why entries.
2. Point the contract to separate reference files for examples (including rejected ones).
3. Ask the assistant to identify the selected section before drafting, and compare the output with the full source to catch dropped qualifications.

## Apply to icm-workshop

- **Adopt** section-level Inputs (file, section, why) as the format for every module contract's Inputs list. This directly serves the one-home-per-fact boundary: shared core files (C1) such as voice rules are referenced by section, never copied into a module.
- **Adopt** the working-input versus reference split: a client's artefact from the previous module is a working input, while pricing, terms and voice from C1 are references, which keeps modules decoupled except through declared Inputs.
- **Adapt** the verification note: a module's first output should show which sections were read, so Jamie can catch a skipped input without running local checks.
