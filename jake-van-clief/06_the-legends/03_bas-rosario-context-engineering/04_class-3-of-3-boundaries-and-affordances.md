# Class 3 of 3: Boundaries and affordances

*THE LEGENDS › 3. Bas Rosario – Context Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

The third class covers what the model is permitted to do and where it believes it is standing, which Bas argues shapes output as much as the instruction does. He proposes four written statements: tools to use, tools to avoid, the environment, and success criteria. A competitor-brief comparison shows how unstated boundaries lead to undated figures, wrong audience, runaway length and a closing line that assumes a draft. The lesson links this to ICM stage contracts as the place where boundaries become checkable handoffs, while stressing that written boundaries are not technical access control.

## Core concepts

- **Four lines usually unwritten:** useful tools or sources, forbidden tools or sources, the environment (draft or final, audience, destination), and a written finish line.
- **Instructions guide; settings enforce:** actual capability depends on the application's tools, permissions and connected accounts. The lesson points to Claude Code permission settings as an example and says the written lines must agree with them.
- **Exclusion with an alternative:** a prohibition works better when paired with what to use instead, such as answering only from named attachments and writing "not in sources" when a fact is absent.
- **Environment shapes tone and finality:** output written for what the model assumes is a throwaway draft differs from output it knows will be released as is, so state which situation applies.
- **Checkable success criteria:** make the finish line inspectable, noting that some checks can be automated and others need a person.
- **Boundaries as the unit of trust:** once a stage's inputs and outputs are known, a check can sit at the point where work passes on. A written boundary does not guarantee compliance and cannot erase learned knowledge.

## Frameworks and methods

1. Name the tools or sources the task may use, confirming they exist and are readable.
2. State what must not be used and what to do instead.
3. Describe audience, destination and draft status.
4. Write a "done when" statement mixing assistant-checkable and human-checkable items.
5. Run once and check the result against all four lines, repairing any boundary that failed.
