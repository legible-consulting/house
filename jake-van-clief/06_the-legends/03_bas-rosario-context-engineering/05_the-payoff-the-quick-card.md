# The payoff: The quick card

*THE LEGENDS › 3. Bas Rosario – Context Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

The payoff gathers the three classes into one reusable "room" and then supplies the series quick card. Bas's framing is that the room is simply the context that made a good Tuesday result possible, written down so it survives into Thursday and into a teammate's session. He demonstrates by writing all seven lines out for a customer-update task. He then marks the limit of rung two: the saved file is static and does not learn, so deciding what to keep over time belongs to the next rung, memory.

## Core concepts

- **The room is context written down:** budget the window, show the style with examples including a rejected one, and fence the permissions and finish line.
- **Worked example:** a weekly customer update specified with a purpose, a closed source list, a ban on unmentioned features, two pasted past updates as the target, a draft-only environment, and a labelled bad sample.
- **Save it as a file or text block:** whether it survives into a new session depends on the product, its memory settings and what is actually loaded; teammates must be handed the current version, and corrections must be added deliberately.
- **Saving does not guarantee identical answers:** check that release facts are current and that example wording has not smuggled in an old promise.
- **Several causes of variation:** inspect both instruction and context, plus model and settings.

## What the quick card covers and how to use it

The card has five parts: the seven-line inventory (with a note that the last line is the one most skipped), the six-heading budget audit with the three-question admission test and notes that limits and costs vary by product, the show-it rule on examples versus adjectives, the fence-it rule on tools, environment and finish line, and a run-it check where you repeat the same prompt in a fresh window and investigate sources, examples, model and settings when the result differs. Use it by writing one room for your most-used prompt, running the prompt fresh, and checking one output against its sources and finish line. It is a reference, not a substitute for the earlier classes on windows and boundaries.

## Claims and evidence

- The Tuesday-versus-Thursday gap was caused by surrounding material — illustrated via the series example — not measured; the page itself says causes can be several.

## Apply to icm-workshop

- **Adopt** the "room as a file" idea as the definition of a module's folder: CONTEXT.md plus references together are the room, and the module starts cold from them (cold-start modules).
- **Adopt** the static-file warning for C2: corrections made in a session only count once written back into the client folder record, otherwise the next cold start loses them. That bridges to the memory series in `04_bas-rosario-memory-engineering/`.
- **Adapt** the run-it check as a validation step in the workspace-builder walk: re-run a module in a fresh session with nothing else changed and inspect differences.
