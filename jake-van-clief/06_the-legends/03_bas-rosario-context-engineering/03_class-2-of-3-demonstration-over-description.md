# Class 2 of 3: Demonstration over description

*THE LEGENDS › 3. Bas Rosario – Context Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

Bas argues that style adjectives such as "professional" or "concise" fail because the model has only the word, not the reader's years of associations, so it returns the average of everything written under that word. Showing a couple of real or clearly fictional examples communicates intended register far better. The most distinctive claim is that a labelled rejected example often sets the boundary more sharply than extra good ones. A customer-reply case runs the same request three ways to show the progression.

## Core concepts

- **A name is not a description:** adjectives are guesses the model fills with the average, which is why "do not sound corporate" can itself return corporate text.
- **Examples are in-context guidance:** they are not retraining and may not persist into another session unless the product has project or memory features.
- **Shape, not facts:** sample replies may contain invented names, dates and refunds; the model must copy the register and structure, never the commitments or details. Every factual claim in the output still needs checking.
- **The rejected example:** label it clearly as "not like this", say why it fails, and keep it separate from the examples to follow. The draft you threw away last week is already a ready-made one.
- **Test, don't assume:** try about two good examples, compare results, and adjust from the failures observed; check that the effect holds on a different case.
- **Missing-fact flag:** the prompt tells the model to flag missing facts for review rather than invent a promise.

## Frameworks and methods

1. Pick two short examples in the same shape as the desired output.
2. Add one labelled reject with a brief reason.
3. Keep source facts and the instruction unchanged while comparing runs.
4. Judge on style, factual accuracy and unsupported promises; keep a version only if it improves the style without copying example facts.

- Examples beat adjectives and a bad example does the most work — demonstrated through a constructed three-version illustration — Bas frames it as something to try and test, not a proven result.

## Apply to icm-workshop

- **Adopt** a one-home-per-fact treatment for examples: voice samples and rejected samples for client-facing documents belong once in the shared core (C1), under the voice and document design area, and each module references them rather than copying.
- **Adopt** the "not like this" habit for S3 Proposal and S1 outreach drafts, where the client-language requirement makes generic brochure tone the likeliest failure; keep each language's good and rejected pair separate.
- Guard the failure Bas names: examples must not leak facts into a different client's artefact, which matters for C2, where each folder holds one relationship's facts.
