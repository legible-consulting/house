# Class 3 of 3: Decay, conflict and correction

*THE LEGENDS › 4. Bas Rosario – Memory Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

The final class addresses what happens when a kept fact stops being true, or two kept facts disagree. Bas reframes memory as a belief the model holds now, not a record of past truth, and traces both stale and conflicting entries to one habit: accumulating. A before-and-after shows six patchwork lines collapsing into three lines that were each replaced in place with a date and source. The lesson gives a short discipline for correcting, dating, handling disagreement and reviewing on a schedule, with the goal that the file stays roughly the same size over time.

## Core concepts

- **Stale versus conflicting:** stale memories were true and the world moved, and they look as correct as ever; conflicting memories arise when someone adds a new line without removing the old one, so the model chooses unpredictably.
- **Accumulating is the root habit:** adding feels like progress, removal feels like loss, so files only grow and every line ages silently.
- **Memory as belief:** the model needs what to believe now, not what was once true. History is not memory; if it matters, store it in a file the room never loads.
- **Replace where it stands:** corrections are written over the old line, never stacked beneath it.
- **Dates and sources are for the human:** a line without a date and origin cannot be doubted, so it cannot be corrected. An expected-to-change line can also say what check to run.
- **Disagreement rule:** the room should instruct the model to flag conflicts and stop rather than choose, which turns a coin toss into a visible file fix.

## Frameworks and methods

1. Correct in place the same day, before the chat closes.
2. Give every line a since-when and a says-who.
3. Write the disagreement rule into the room's always-loaded section.
4. Review monthly with three questions per line (still true, since when, says who), then update or delete failures and ask whether long-unused lines are worth keeping.
5. Aim for a file about the same size next year as today.

## Claims and evidence

- A file three times larger is a diary again — rule of thumb, no evidence.
- Stale lines go bad the week you stop opening the file — a prediction from the author.

## Apply to icm-workshop

- **Adopt** correct-in-place with date and source as the update rule for every C2 client record, so a salesman, Jamie or the client sees one current line rather than a layered history.
- **Adopt** the monthly review rhythm in the monthly close and quarterly estate audit that C3 already plans; add a "still true, since when, says who" pass over client records and shared core facts. D4 conformance could report files with undated lines.
- **Adopt** the disagreement rule in module contracts that read multiple Inputs: if two sources conflict, stop and report rather than decide, consistent with human gates.
- **Adapt** the "history goes in a file the room never loads" idea: keep git history as the record, and keep the loaded files as belief only. This stays within the boundary that rules carry their own why and date.
