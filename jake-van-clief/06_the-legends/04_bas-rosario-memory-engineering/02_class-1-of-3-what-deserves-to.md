# Class 1 of 3: What deserves to persist

*THE LEGENDS › 4. Bas Rosario – Memory Engineering · Author: Bas Rosario · Source: text lesson*

## Summary

Bas teaches a selection discipline for memory: separate durable items from disposable ones, then make each durable candidate pass three tests. He uses the image of a handover note for someone covering your desk, which holds only the few things that changed and could trip them up. Walking one week of a customer-update workflow, he shows an eight-entry diary-style memory failing the tests and a three-line memory passing. The thesis is that most memory fails by keeping too much, and that each kept line should be a rule, fact or preference, never a diary entry.

## Core concepts

- **Durable versus disposable:** disposable things mattered only to their moment (rejected drafts, the route to an answer); durable things would have to be said again for future output to be right. A practical test is whether you would type it again in a fresh window.
- **Three tests for kept items:** it must be retrieved (visible when needed, with short notes read whole and long ones skimmed), trusted (carrying when and from whom, so staleness is detectable), and paid for (it occupies a recurring seat in every future window).
- **Decision, not story:** keep the outcome of a decision and drop the narrative of reaching it; vague records such as "not this week" lose meaning over time.
- **Material is not memory:** that week's release notes belonged to that week's room only.
- **Promotion from the room:** a recurring "what bad looks like" line from the context series can be promoted into memory when you keep retyping it.
- **Format:** one line per item as a rule, fact or preference; diary entries are the failing form.

## Frameworks and methods

Put each candidate through a four-step filter and drop it at the first failure: Would you have to re-type it in a new window? Is it a statement about what comes next rather than a log of something that happened? Will it hold a month from now, and is the origin and date written on the line? Does it justify occupying space every time the room is loaded? Survivors are written as one line each under a heading in the room's file, the room is run for a week with nothing added, and a second list tracks anything retyped anyway (class two's starting point).

## Claims and evidence

- Most memory fails by keeping too much rather than too little — argued via a constructed week; no data.
- The author predicts two of the three learner items survive — a stated guess.

## Apply to icm-workshop

- **Adopt** the four-question filter as the admission rule for what goes into a client folder record (C2): a client's confirmed preferred name, language and terms qualify; call-by-call narration does not. Each line should carry its date and source, which matches the goals file's "a rule carries its own why and date."
- **Adopt** the durable versus disposable split for module outputs: only artefacts a downstream module declares as an Input are durable handoffs; drafts and rejected versions stay out of the folder record.
- **Adapt** the "Remember" heading idea for the top of each client folder's status file so the first screen is short enough to be read whole.
