# 3.4 Repeat the Workflow and Check the Results

*AI Animations & Workflows › Module 3: Browser Workflows · Author: Jake Van Clief · Source: text lesson*

## Summary

Once a pilot edit has worked, the same checklist is applied to a small named batch of pages. The instruction is to supply the URLs and the exact change per page, inspect any page whose layout differs before reusing the steps, and require one report row per page. The point is that unknowns are never reported as passed and each result can be opened and verified.

## Core concepts

- **Boundaries per run:** page URLs, exact change for each, before record, review criteria, and any manual handoff travel with the task.
- **Stop per page, not per batch:** a materially different page is halted and explained while the others continue.
- **Evidence-based reporting:** one row per page with change, saved URL, checks passed, manual steps and unresolved items.
- **Test what the learner experiences:** an administrator's view does not prove a member can download; a desktop capture does not prove mobile layout.
- **Maintain the routine:** when a login, label or layout changes, update that step and keep the last working version.
- **Saved shortcuts are not proof:** a stored recording or scheduled time does not show a successful run.
- **Planning honesty:** separate the mechanical edit from the work around it.

## Frameworks and methods

Read, preserve, change, save, reopen, compare, repeated on three named pages with explicit stop conditions.
