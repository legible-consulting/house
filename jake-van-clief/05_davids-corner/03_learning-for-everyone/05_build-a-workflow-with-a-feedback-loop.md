# Build a Workflow With a Feedback Loop

*David's Corner › Learning for Everyone · Author: David's Corner (author not stated; inspired by Diana Hu's Y Combinator talk) · Source: text lesson*

## Summary

An overview of closing a loop between instructions, work, observed results and the next decision, inspired by a Y Combinator video. The cycle is outcome, one bounded piece of work, comparison with criteria, recorded corrections, next step. It recommends shared briefs, task status and decision records, minimal access for assistants, and a named human owner even when an agent coordinates. It cites one company's approach of scenario-based validation instead of human code review as a specific case, not a general recommendation.

## Core concepts

- **Bounded loop:** one piece of work per cycle, compared against stated criteria.
- **Accountability roles:** builder, outcome owner, team lead; they can overlap but do not vanish.
- **Least access:** recording everything is not a prerequisite; respect retention rules.
- **Economics test:** track time to accepted result, correction rate, model cost and maintenance; higher spend only pays if results justify it.

## Claims and evidence

- Extreme productivity multipliers in the source material — page says not to expect them — unverified.
- One firm's scenario-testing without code review — vendor writeup — an approach, not evidence for dropping review.

## Apply to icm-workshop

- **D2 SDLC pipeline:** the loop maps to ticket to release with a recorded correction step; live status and UAT sign-off are the observed-result half.
- Boundary reminders: gates are human; CI is truth. Reject dropping human review as a model.
- Tension 5 in the goals (cost per engagement) is the same measure this page asks for; hours and model spend need a recorder.
