# This one's golden...Vibe coding rules

*David's Corner › Must Have Resources · Author: David (curating Noah Taylor's vibe-code-rules.md) · Source: text lesson*

## Summary

David points to a rules file Noah Taylor wrote for his own coding projects, attached with Noah's original post. David's praise centres on visibility: folders and Markdown make expectations explicit, coding rules are kept apart from unrelated work, and the author invites improvement. The lesson does not tell you to adopt the file; it tells you to take one rule that answers a problem you have actually seen, keep its attribution, narrow it, and define what success looks like.

## Core concepts

- **Adapt one, not all:** choose a rule tied to an observed problem.
- **Explicit loading:** dropping a file in a folder does not prove an assistant read it; supply it explicitly and learn each tool's own instruction-file convention.
- **Review before applying:** ask the assistant to flag conflicts with existing project instructions and propose a scoped version without editing.
- **Credit and terms:** check the source's terms before redistributing.

## Apply to icm-workshop

- Adopt the "one rule, scoped, with a check" method for D4: a conformance report should confirm each tier template's rules are actually loaded, not just present as files.
- Adapt for rule hygiene: the goals file requires every rule to carry its why and date, which this lesson's "record what success looks like" echoes.
