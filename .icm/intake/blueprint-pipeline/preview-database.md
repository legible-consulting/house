# Stub: A Neon build's previews read the base database, a preview with a migration gets its own Neon branch, and production migrates on the merge or on the promotion

- feature-slug: preview-database
- epic: blueprint-pipeline
- sequence: 8 of 13
- depends-on: scripts
- complexity: high
- priority: P0

## Problem

The UAT contract gives every preview a Neon branch through the Vercel integration, allows a schema-only `uat` branch in one project, and says a session never dispatches `promote.yml`. A `uat: no` build has no database rule at all. Not every build runs Neon: sustentus runs MongoDB, and it will join the estate. Jamie's shape is one mechanism for every build on Neon, and nothing for the others, so that a non-Neon build shows what the blueprint lacks. The base database is UAT's with a UAT environment and production's without one. Every preview reads the base. A preview whose diff carries a migration gets a Neon branch cut from the base. Neon cleanup deletes only such a branch. Production migrates on the merge without UAT, and on the session's promotion with UAT.

## Proposed change

One contract, `.icm/database/CONTEXT.md`, rendered when the build answers `neon`. `preview-db.sh`, `preview-db.yml` and `neon-cleanup.yml` arrive with it. The UAT contract keeps the environments, the batch, the sign-off and the promotion, and points at the database contract for the rest. `uat-db.sh` leaves. Two questions join the bank: `database`, a choice, and `migrations_path`, asked on `neon`. Any answer but `neon` renders no database file.

- [ ] `copier.yml`: `database` (str, `choices: [none, neon, mongodb, other]`, default `none`, asked for every build, not a workspace). Help: the database the build runs on. `neon` renders the database contract, the preview-branch script and the two workflows. Any other answer renders no database file, and the answer stays in `.copier-answers.yml` so the blueprint can learn what those builds need. `migrations_path` (str, default `migrations`, asked when `database` is `neon`). Help: the folder the migration files live in, relative to the repo root, for example `migrations` or `drizzle`. A validator refuses an absolute path and an empty value.
- [ ] `template/{% if not workspace %}.icm{% endif %}/{% if database == 'neon' %}database{% endif %}/CONTEXT.md`, under 90 lines, Inputs, Process, Outputs. It says the two shapes in one table. With UAT: one Neon project for production and one for UAT. The base is the UAT project's default branch. The Vercel Preview and `uat` environments read it. The Neon integration is connected to Production only, or not at all. Without UAT: one Neon project. The base is its default branch, production's database. The Vercel Preview environment reads it. A preview without a migration reads and writes the base's rows, and a tester knows it (why: Jamie's shape, 2026-10-27, and a preview that changes no schema needs no copy).
- [ ] The branch rule, the same in both shapes: a pull request whose diff touches `<migrations_path>/**` gets the Neon branch `preview/<git branch>`, cut from the base with its data, by `preview-db.yml`. The branch and its three variables leave when the pull request closes.
- [ ] The migration rule: `package.json` names `db:migrate` and `db:verify`. The build's `vercel-build` script runs `db:migrate`, then `db:verify`, then the build when `MIGRATE_AT_BUILD` is `1`. Otherwise it only builds. The variable means this deployment owns its database. With UAT: the `uat` environment carries it always and production never, because `promote.yml` migrates production. Without UAT: the Production environment carries it always, so the build of `main` migrates production and then serves it. A preview branch carries it from `preview-db.sh`. A plain preview never carries it (why: a preview without its own branch must not migrate the base, and the first build of a pull request may run before its branch exists, so a build migrates only where the variable says the database is its own · 2026-10-27).
- [ ] `.icm/scripts/preview-db.sh create <git branch>`: creates `preview/<git branch>` from the base when it does not exist, sets `DATABASE_URL`, `DATABASE_URL_UNPOOLED` and `MIGRATE_AT_BUILD=1` on the Vercel Preview environment scoped to that git branch, and redeploys the branch's latest preview deployment. Idempotent. `delete <git branch>`: deletes the branch and the three scoped variables when they exist, and says what it found. `status <git branch>`: prints both. `NEON_PROJECT_ID` names the one project the branches are cut from: the UAT project with UAT, the production project without. The transports are `lib/neon.sh`, rendered on `neon`, and `lib/vercel.sh`, rendered on `neon` or `uat`. A token never reaches a command line.
- [ ] `.github/workflows/preview-db.yml`, on `pull_request` (opened, synchronize, reopened), `paths: ["<migrations_path>/**"]`, runs `preview-db.sh create "$GITHUB_HEAD_REF"`. `.github/workflows/neon-cleanup.yml`, on `pull_request` closed, runs `preview-db.sh delete "$GITHUB_HEAD_REF"`. A pull request that made no branch: the script says so and exits 0. Both render on `neon`.
- [ ] `.icm/uat/CONTEXT.md`: § The database becomes one paragraph. With `database: neon` it points at `.icm/database/CONTEXT.md` and names the UAT project as the base. With any other answer the database is the build's own, the UAT environment still reads a UAT database the build provides, and this contract says nothing more about it. `promote.yml`'s migrate job keeps `--if-present`, so it runs the build's own `db:migrate` on any database or skips. `promote.yml` keeps its three jobs, and its header says `promote.sh run --tag` dispatches it on the client's recorded word. "Nothing starts this workflow but Jamie" becomes "nothing starts this workflow but `promote.sh run`". `uat-db.sh` is deleted, with its lines in the contract, `README.md` and `conventions/README.md`.
- [ ] `.env.example` renders on `neon` or `uat`. On `neon` it names `MIGRATE_AT_BUILD`, `NEON_API_KEY`, `NEON_PROJECT_ID`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED` with the environments each one reaches. On `uat` without `neon` it names the Vercel variables only.
- [ ] § Setup, once, in the database contract, for each shape: the Neon project or projects, the Preview variables from the base, `MIGRATE_AT_BUILD=1` on `uat` or on Production, the integration on Production only, the Actions secrets and variables, `package.json`'s three scripts. The UAT contract's own setup list keeps only the environments and the promotion.

A redeploy is `POST /v13/deployments` with the deployment's `gitSource`, or `vercel redeploy <url>`. Neon's `POST /projects/{id}/branches` with `parent_id` copies the data by default. A migration at build runs while the previous deployment still serves, so a migration must be forward-compatible with the code it replaces. The contract says so in one line.
